# Publication Metadata Consumption — Phase 1 Blueprint

Status: proposed, awaiting Founder Office approval. Blueprint only —
no code, no schema, no migrations, no serializer changes, no artifact
or release changes. Authorized by the Founder Office Publication
Metadata Consumption Phase 1 directive at baseline `3253a7a` (hosted
ledger 35/35). Amended, never silently rewritten.

Governing canon: all four constitutions and the terminology canon
(including the Publication Metadata & ISBN ratifications), the
Production Bridge Phase 1 Blueprint — Revision 2, the Publication
Release Phase 1 Blueprint, the Print Production Phase 1 Blueprint,
the Publication Metadata & ISBN Phase 1 Blueprint, and the as-built
corpus through `docs/operations/publication-metadata.md`.

Convention: **(existing)** marks verified repository behavior;
**(new)** marks architecture proposed here.

---

## 1. Executive Overview

The institution now governs two parallel truths about a book: what it
*is* (the Candidate → Artifact → Release chain, deterministic and
evidence-gated **(existing)**) and how it is *described* (the
versioned Bibliographic Record and the evidence-backed ISBN Registry
**(existing)**). Nothing yet connects them: an artifact's bytes carry
no commercial description, and no record could say which description
they carried if they did.

This blueprint defines the bridge — **Metadata Consumption**: the
explicit, immutable, per-artifact act by which one finalized
Bibliographic Record version and, where honestly possible, one
evidenced external identifier become version-pinned inputs to future
artifact generation. The governing principle:

> **An Artifact must never depend on "whatever metadata is active
> now." It permanently identifies the exact metadata inputs used when
> its bytes were generated.**

One consumption record family (the companion-record discipline the
print program established **(existing pattern)**), two conceptual
serializer successors (hgp-epub and hgp-print next versions), one
deterministic copyright page, and explicit seams for everything this
blueprint refuses to solve: Editions, ONIX, covers, distribution.

## 2. Purpose and Lifecycle Scope

Home ground: the moment of **artifact generation** on the Publication
Desk. Consumption is not a lifecycle stage, not an approval, and not
a release act — it is an input-binding fact of each generated
artifact. Everything upstream (drafting, finalizing, activating
metadata; recording ISBNs) and downstream (release, channels) is
untouched.

## 3. Existing Architecture Inherited

Treated as established, not redesigned:

- The Book and its governed facts; the versioned Bibliographic Record
  with immutable finalized versions, one active pointer, restore by
  re-pointing **(existing)**.
- The ISBN Registration registry: recording and forward-only
  correction of externally governed identifiers with evidence; **no
  assignment path** (Founder boundary) **(existing)**.
- The Publication Candidate: frozen composition + frozen title-page
  facts (title, subtitle, author display, language), pbc-v1
  fingerprint, dual TS/SQL computation with refuse-on-mismatch
  **(existing)**.
- The Publication Artifact: immutable, success-only, candidate
  id/number/fingerprint + serializer identity/version + checksum +
  actor/moment; regeneration links; append-only attempts; DB-enforced
  eligibility (open candidate, fingerprint-bound open Author Approval
  + Imprint Authorization) **(existing)**.
- hgp-epub 1.0.0 (OPF: `urn:uuid:{candidateId}` unique identifier,
  title, creator, language, dcterms:modified from the presentation
  moment) and hgp-print 1.0.0 over hgp-layout 1.0.0 (title page,
  fixed-grid pagination, print_artifact_provenance companion)
  **(existing)**.
- The Release Record and its channel/evidence architecture
  **(existing)**.
- Append-only history, RLS-first, no service_role, human publication
  authority, structural AI exclusion **(existing)**.

## 4. Terminology

- **Metadata Consumption** — the act, recorded per artifact, of
  binding specific governed metadata inputs into generated bytes.
- **Consumed Bibliographic Version** — the one finalized
  Bibliographic Record version an artifact's bytes derive from.
- **Identifier Consumption** — the recorded fact that one eligible,
  externally evidenced ISBN was embedded in an artifact, with the
  identifier and its evidence state snapshotted at that moment.
- **Metadata Pin** — the permanent artifact-side reference to the
  Consumed Bibliographic Version: version identity, version number,
  and metadata fingerprint. A pin never re-points.
- **Metadata Readiness** — the deterministic facts about whether and
  how governed metadata can enter a target output; facts, never a
  verdict **(existing readiness discipline)**.
- **Artifact Metadata Provenance** — the immutable companion record
  holding an artifact's Metadata Pin and Identifier Consumption.

## 5. Central Consumption Architecture

**(new)** Future serializer versions accept a second frozen input
beside the candidate: the Consumed Bibliographic Version (and at most
one Identifier Consumption). The binding is recorded in a dedicated
**Artifact Metadata Provenance** record — one per artifact, written
atomically with the artifact in the sanctioned export transaction,
immutable from birth — exactly the companion-record shape
print_artifact_provenance already established **(existing pattern)**.

The relationship map:

```
Book ──► Bibliographic Record versions v1..vN (existing)
  │              │ one finalized version, pinned
  │              ▼
  ├─► Candidate ─► Artifact ◄─── Artifact Metadata Provenance (new)
  │   (existing)   (existing)      metadata pin + identifier consumption
  │                    │
  │                    ▼
  └───────────────► Release (existing, untouched; inherits consumption
                     provenance transitively through the artifact)
```

No hidden coupling: candidates never reference metadata versions;
metadata versions never reference candidates; only the artifact —
the rendering act — binds them, permanently.

## 6. Bibliographic Record Version Pinning

- **Only finalized versions are consumable.** Draft metadata cannot
  enter an official artifact — structurally, because the pin may only
  reference a finalized version (the active-pointer discipline
  **(existing pattern)**).
- **Default selection: the active finalized version** at the moment
  of generation. No ceremony, no re-entry.
- **Historical finalized versions are intentionally selectable** by
  the same human who lawfully invokes generation, with an explicit
  recorded reason (the change-summary discipline **(existing
  pattern)**). Restores make this rarely necessary, but a
  deliberately historical rendering must be honest, not impossible.
- **The pin preserves version identity, version number, and the
  metadata fingerprint (§9)** — identity for the record, number for
  the human, fingerprint for byte-level reproducibility.
- **Divergence is a readiness fact, and identity coherence is a
  gate.** Divergence between the consumed version's derived snapshot
  and the live Book is reported, never blocking by itself (the
  candidate-divergence stance **(existing)**). But if the consumed
  version's derived identity facts (title, subtitle, author display,
  language) disagree with the **candidate's frozen title-page facts**,
  generation of releasable artifacts fails closed — the artifact
  would state two identities for one work. Print proofs (internal,
  unreleasable **(existing)**) may proceed with the disagreement
  reported.

## 7. Candidate Boundary

The Candidate remains exactly what it is **(existing, unchanged)**:
the frozen manuscript/publication context. Explicitly:

- A sales-description change does not create a candidate.
- Keyword and category changes do not create a candidate.
- Contributor/commercial metadata changes do not create a candidate.
- Only manuscript/publication-context change under existing candidate
  rules ever creates one.
- Metadata versioning runs on its own clock, independent.

**Ownership where facts overlap:** the Candidate owns what the
manuscript's own pages say — title-page content, package title,
creator, language continue to render from frozen candidate facts
exactly as in 1.0.0 serializers **(existing)**. The Consumed
Bibliographic Version supplies only what the candidate structurally
cannot know: publisher/imprint display, description, the contributor
list beyond the byline, copyright facts, the identifier. No fact in
an artifact has two sources; the §6 coherence gate guarantees the two
frozen records describe the same work state.

## 8. Metadata Consumption Identity

Evaluated homes for "Artifact A consumed version Y and identifier Z":

- *Columns on publication_artifacts* — rejected: nullable creep on a
  shared immutable table; 1.0.0-era artifacts have no consumption and
  their honest history is the absence of a record, not null columns.
- *Inside print_artifact_provenance* — rejected: consumption is
  format-agnostic; EPUB would need a parallel structure.
- **A dedicated Artifact Metadata Provenance record — recommended:**
  one per consuming artifact, keyed to the artifact, immutable,
  written atomically at export success, format-agnostic (what differs
  by format is captured by serializer version + metadata fingerprint,
  not by the record's shape). Absence on an artifact means the
  serializer version predates consumption — self-interpreting history.

One artifact → exactly one consumed metadata state: one pinned
version, at most one identifier consumption.

## 9. Metadata Fingerprint Determination

**Recommended: yes** — a canonical content fingerprint of the
consumed metadata, in the pbc-v1 discipline **(existing pattern)**:
a versioned canonical serialization (algorithm id recorded, e.g. a
"bmv-v1" canon defined at implementation) over exactly the
consumable content in fixed field order — derived facts; authored
descriptions; keywords in stored order; categories in stored order;
copyright year and line; publication notices; contributors in
position order with role and derived flag — excluding uuids,
timestamps, and version numbers (provenance, not content). Database
identity (version id) says *which* record; the fingerprint proves
*what it contained* and makes byte reproducibility auditable forever.
Finalized versions are immutable **(existing)**, so the fingerprint
is stable and recomputable at any later moment; Phase 2 decides
whether it is additionally stamped at finalization. No hashing is
implemented here.

## 10. ISBN Consumption Eligibility

The ISBN boundary remains fully binding **(existing)**: the registry
records; nothing assigns. Consumption adds no assignment — it is a
per-artifact historical restatement of an externally evidenced fact.

Deterministic eligibility facts (readiness vocabulary, repository
terms):

- **eligible** — the registration is current (`recorded`), carries an
  externally evidenced assignment, and its evidence establishes the
  work relationship and a format relationship compatible with the
  target artifact (§11).
- **formatUncertain** — current and evidenced for the work, but the
  verbatim external format wording does not establish the target
  artifact's format class.
- **evidenceInsufficient** — externally assigned, but the evidence
  does not establish the relationship claimed for this use.
- **recordedOnly** — current but not externally assigned: an
  identifier on file with provenance, no assignment fact to restate.
  Not consumable (consuming it would assert an assignment that does
  not exist).
- **nonCurrent** — corrected, superseded, or invalidated. Never
  consumable; the replacement registration stands on its own facts.
- *Structurally invalid* identifiers cannot exist in the registry
  (DB CHECK **(existing)**), so no eligibility class is needed.

**Absence of ISBN is valid, always.** No readiness fact ever demands
one; no fallback invents one.

## 11. ISBN Evidence and Format Compatibility

What the evidence must establish for consumption into a specific
artifact: the identifier (structural validity is already law), the
work (external title consistent with the Book this candidate
renders), and the format relationship (the verbatim
`external_format_wording` **(existing)** corresponds to the artifact's
format class — ebook wording for EPUB, print wording for print-pdf).

**The format correspondence is a human judgment, never a string
inference.** Readiness surfaces the verbatim wording beside the
target format; the human generation authority decides whether to
consume. The system never auto-selects an identifier, never matches
wording programmatically, and defaults to no identifier. Registrant
evidence (`external_registrant`) is displayed as recorded; a
registrant other than the institution is a fact the human weighs, not
a computed block — the registry records external reality
**(existing)**, and consumption restates it.

## 12. Edition Boundary

**Honest consumption is possible before Edition — exactly and only
for externally evidenced assignments.** The consumption act creates
no standing Book+format binding: the format relationship lives in the
external evidence (where it came from) and in the per-artifact
consumption record (where it was restated), never as a reusable
internal assignment, never as inventory, never as Edition surrogate.
Each artifact's identifier consumption is a dated historical fact,
not a binding future artifacts inherit.

What must remain deferred: any institution-acquired ISBN (none exist
— no acquisition or assignment mechanism exists **(existing)**)
cannot be consumed until Edition architecture carries assignment
under its own authorization. If the institution acquires ISBNs before
Editions exist, those identifiers can be *recorded* but not consumed
— the boundary is stated here so it cannot be weakened by
implementation pressure. No interim Book+format assignment model is
created. No blocking case remains for the externally evidenced path
(§35).

## 13. EPUB Metadata Consumption

Conceptual next version of hgp-epub. Package metadata additions from
the Consumed Bibliographic Version — each passing the necessity test,
nothing added merely because EPUB permits it:

- `dc:publisher` — the imprint constant (Huerta Group Publishing)
  **(existing constant)**.
- `dc:description` — the publication description, when present;
  absent stays absent.
- `dc:contributor` — the version's non-derived contributors in
  position order; role refinements only where the ten governed roles
  map cleanly onto standard vocabulary (they were chosen mappable
  **(existing)**); a role without a clean mapping ships as a plain
  contributor, not a stretched code.
- `dc:identifier` — an additional identifier when an eligible ISBN is
  consumed (§14).

Unchanged and candidate-sourced **(existing)**: `dc:title`,
`dc:creator` (the byline), `dc:language`, `dcterms:modified`, the
title-page XHTML, navigation labels, and all visible content — this
phase adds **no new visible EPUB content**. Subtitle stays out of
package metadata (no implemented consumer; the visible title page
already carries it). Keywords and categories stay out of the package
(their consumer is future channel metadata, not the reading system).
No ONIX semantics enter EPUB.

## 14. EPUB Identifier Strategy

The package `unique-identifier` remains the institutional
`urn:uuid:{candidateId}` **(existing)** in every case — deterministic,
honest, never masquerading as an external identifier, and stable
under every ISBN future. Cases:

- **Eligible ISBN consumed** — added as a second `dc:identifier`
  (scheme-identified as an ISBN); the unique-identifier does not
  change.
- **No ISBN** — the package is complete and valid as today; absence
  is absence.
- **Format compatibility uncertain / evidence insufficient /
  recorded-only** — not consumed; same as no ISBN.
- **Corrected or superseded** — non-current, not consumable for new
  artifacts; historical artifacts keep the identifier they actually
  embedded (§20, §21).

Nothing fabricates an external identifier, ever.

## 15. Print Metadata Consumption

Conceptual next version of hgp-print. Byte-affecting additions,
bounded:

- **The copyright page (§16)** — the first metadata-driven
  front-matter structure, occupying the title-page verso that today
  is structurally available.
- **The imprint line on the title page** — the governed imprint
  constant at the foot of the existing title page; conventional,
  institutional, no per-book data entry.

Everything else is preserved exactly: deterministic pagination on the
fixed grid, Print Profile independence (metadata is not profile;
profiles stay per-institution, versioned, immutable **(existing)**),
candidate-only manuscript content, the print provenance companion,
recto opening rules, the governed repertoire and fail-closed
unsupported content **(existing)**. Front matter growth shifts
pagination — deterministically, under the new serializer version,
producing new artifacts; nothing rewrites an existing interior.

## 16. Deterministic Copyright Page

**Determination: yes** — Phase 2 introduces the copyright page.
Allowed inputs, all governed, in a fixed deterministic order, each
line omitted entirely when its fact is absent:

1. Title (and subtitle) restated — candidate frozen facts.
2. The copyright line as recorded (`copyright_line`), else a line
   composed only of the recorded copyright year and the derived
   author display — no fact, no line.
3. Publisher identity: the imprint, and the legal entity where the
   recorded facts warrant it — constants **(existing)**.
4. The consumed ISBN, labeled as such, when an Identifier Consumption
   exists.
5. Publication notices (`publication_notes`) as recorded.

Prohibited — structurally absent, not merely discouraged: copyright
registration numbers; fabricated ISBNs; Edition statements; printing
numbers/lines; Library of Congress data; distribution addresses;
retailer data; rights statements not governed by the record; **"All
rights reserved" or any legal formula unless repository authority
establishes it as a governed fact first**. Missing facts remain
absent — the page renders only what the institution actually knows.

## 17. Artifact Reproducibility Equation

Refined from repository evidence:

```
frozen Candidate (composition + title-page facts, pbc-v1 fingerprint)
  + pinned finalized Bibliographic Version (bmv fingerprint)
  + Identifier Consumption (zero or one, snapshotted)
  + institutional constants as carried by the serializer version
  + format/profile inputs (print: profile version + font inputs)
  + serializer identity/version (print: + renderer version)
  = deterministic Artifact bytes (one checksum, forever)
```

Every input is identifiable, immutable or historically recoverable,
provenance-bound, and reproducible. **Consequence (load-bearing):**
the reproducibility uniqueness law — one checksum per (candidate,
format, serializer version) **(existing)** — must widen to include
the consumed metadata identity, because one candidate may honestly
yield different bytes under different pinned versions or identifier
consumptions. Phase 2 defines the widened key; the law itself (same
inputs → same bytes, divergence refused at the database) is
unchanged.

## 18. Serializer Version Evolution

The versioning law stands **(existing)**: byte-affecting change
requires a new version. Metadata consumption changes bytes and the
input contract — conceptually **hgp-epub 2.0.0** and **hgp-print
2.0.0** (exact numbers follow the recorded convention at
implementation). hgp-epub 1.0.0 and hgp-print 1.0.0 retain their
exact behavior indefinitely; their artifacts remain interpretable as
*Candidate X through serializer Z* with no consumption record —
honest history. No backporting of metadata consumption under existing
version identifiers, ever.

## 19. Artifact Provenance Requirements

Once consumption exists, an artifact's permanent provenance
comprises: candidate id + number + fingerprint **(existing)**;
serializer identity + version **(existing)**; format/profile
provenance (print companion **(existing)**); generation actor +
moment **(existing)**; checksum + byte size **(existing)**; **(new)**
the Metadata Pin (version id, version number, metadata fingerprint,
canon algorithm id, selection basis — active-by-default or
historical-with-reason) and the Identifier Consumption (§20) when one
occurred. Self-interpretable forever: later activation changes,
metadata versions, ISBN corrections, and eventual Edition
architecture alter nothing recorded here.

## 20. Identifier Consumption Provenance

Preserved per consuming artifact: the ISBN Registration reference;
the normalized ISBN-13 **snapshot** and as-entered form; the
registration's disposition at consumption; a reference to the
external-assignment evidence relied upon (and its verbatim format
wording at that moment). Snapshots exist so that no later correction
can make a historical artifact appear to have consumed anything other
than what its bytes actually embed: the registry row may become
`corrected`; the artifact's record still states the identifier it
carries, marked by the snapshot as the fact it was then.

## 21. Historical Metadata-Change Behavior

```
Metadata v1 ──► Artifact A          (pinned to v1, forever)
Metadata v2 becomes active
```

- A remains pinned to v1; A's bytes and provenance do not change.
- Regenerating A — candidate + v1 + A's serializer version + A's
  identifier consumption — reproduces A's bytes exactly (the
  regeneration-link discipline **(existing)**); checksum divergence
  is refused at the database **(existing)**.
- Artifact B may be generated from v2: a new artifact, new pin, new
  checksum, its own history.
- Nothing ever silently rebinds A to v2. A later ISBN correction is a
  readiness fact for *future* artifacts and touches no historical
  record.

## 22. Release Provenance Seam

Release architecture is untouched in this phase **(existing)**. A
release binds an artifact; the artifact carries its Metadata Pin —
so every release already inherits, transitively and immutably, which
metadata version and identifier its released bytes embody. A future
bounded Release enhancement (its own authorization) may additionally
record the metadata version *active at declaration time* where
channel work needs it. Four states remain permanently distinct, never
conflated into a "current publication metadata": (1) metadata used to
generate the artifact; (2) metadata active at release; (3) metadata
transmitted to a channel; (4) metadata active now.

## 23. Future Channel/Distribution Metadata Seam

Distribution, when authorized, submits (artifact + its consumed
metadata version + a channel-specific transformation) and preserves
exactly what was transmitted as evidence — the Release channel
architecture's existing discipline **(existing)** extended by its own
blueprint. Nothing here designs retailer mappings, ONIX messages,
channel schemas, or payloads; the seam is the pinned, fingerprinted
metadata version those systems will read.

## 24. Author-First Workflow

Develop the Book once; governed information carries forward
**(standing principle)**. The author drafts and finalizes the
Bibliographic Record once **(existing)**; generation surfaces the
active finalized version, its readiness for the target output, and
identifier eligibility — honestly, with no re-entry. Derived Book
facts flow automatically **(existing)**. Explicit human choice is
required exactly where authority or ambiguity demands it: selecting a
historical version (with reason) and consuming an identifier (a
deliberate act, never automatic). No per-serializer metadata forms
exist or may be built.

## 25. Metadata Selection Authority

Selection rides the existing generation acts — no new ceremony:

- Whoever may lawfully invoke generation **(existing: export under
  open approval + authorization; print proof under preparation
  authority; production under the full chain)** selects the metadata
  version, defaulting to the active finalized version.
- Historical finalized selection: the same authority, with an
  explicit recorded reason.
- Identifier consumption: the same authority, as a deliberate
  opt-in per generation (§11).
- Draft selection: impossible, structurally (§6).
- **AI never selects** — no AI path reaches generation or selection
  **(existing structural exclusion, preserved)**.

## 26. Metadata Consumption Readiness

Deterministic facts in the Readiness Report discipline **(existing:
pass / attention / info, never a verdict)**, computed purely:

- active finalized metadata exists / does not exist;
- selected version is finalized (always true structurally; stated);
- selected version is historical (non-active) — with its reason;
- selected version diverges from current Book facts (per cause);
- selected version disagrees with candidate frozen identity (the §6
  gate, reported before it blocks);
- serializer-required metadata present (the next versions require
  none beyond what exists — absence of optional fields is `info`,
  never fabricated);
- ISBN: absent (valid), eligible, recordedOnly, formatUncertain,
  evidenceInsufficient, nonCurrent;
- contributor structure valid (roles in vocabulary, ordering intact
  — structurally guaranteed, stated).

Readiness never finalizes, activates, assigns, selects identifiers,
or authorizes anything.

## 27. Failure Semantics

Fail closed wherever the wrong metadata or identifier could produce a
materially false artifact:

- no finalized metadata version when generation requests consumption
  → refuse (`metadata_version_required`-class);
- draft or nonexistent version selected → refuse, structurally;
- candidate/metadata identity disagreement on a releasable
  generation → refuse (§6);
- identifier requested but not eligible (recordedOnly,
  formatUncertain, evidenceInsufficient, nonCurrent) → refuse the
  identifier consumption; generation may proceed without it only by
  explicit choice;
- metadata fingerprint mismatch at recording (computed vs recomputed)
  → refuse the write (the pbc-v1 refuse-on-mismatch discipline
  **(existing pattern)**);
- serializer-version mismatch between requested behavior and
  recorded identity → refuse;
- historical reconstruction impossible (pinned version unreadable) →
  refuse regeneration rather than substitute;
- optional metadata absent → absent output, never fallback text.

Failed generations follow the existing append-only attempt audit with
sanitized codes **(existing)**.

## 28. RLS / Authority Boundaries

Artifact Metadata Provenance follows artifact visibility exactly
**(existing shape)**: the book's author reads their own; staff read
all; rows are written only inside the sanctioned export transaction
by the acting generator; immutable from birth; no delete grants; no
service_role. Registry authority is unchanged (staff-only acts
**(existing)**). Metadata authority is unchanged (owner-or-staff
draft/finalize/activate **(existing)**). AI reaches none of it.

## 30. Minimum Future Operational Surface

An authorized user must be able to see, at generation time: the
candidate; the active finalized Bibliographic Record version (and any
selectable historical finalized versions); the exact version that
will be consumed; divergence and coherence facts; identifier
availability and eligibility with verbatim evidence; the serializer
version; what the metadata will add to EPUB/print. And afterward: any
artifact's consumed version, identifier, and fingerprints beside its
existing provenance. Conceptual actions: use active version;
intentionally choose a historical finalized version (reason
required); inspect metadata before generating; generate with pinned
metadata; inspect artifact metadata provenance. No screens or
components are designed here.

## 31. Architectural Invariants

1. Official artifact metadata comes from one explicit finalized
   Bibliographic Record version.
2. Draft metadata cannot enter official artifacts.
3. The artifact-to-metadata-version binding is immutable.
4. Later metadata activation cannot rewrite historical artifact
   provenance.
5. Later metadata edits cannot mutate historical artifact bytes.
6. Regeneration under historical pinned inputs remains reproducible.
7. Candidate identity is independent of commercial metadata versions.
8. Commercial metadata change alone never creates a candidate.
9. ISBN absence is valid.
10. ISBN consumption requires evidence sufficient for the exact
    claimed use.
11. No ISBN may be fabricated.
12. No internal ISBN assignment exists before Edition architecture.
13. Format compatibility is never inferred without evidence.
14. Corrected/superseded ISBN facts remain historical.
15. Historical artifacts retain the exact ISBN actually consumed.
16. New serializer behavior requires a new serializer version.
17. hgp-epub 1.0.0 behavior remains frozen.
18. hgp-print 1.0.0 behavior remains frozen.
19. Every byte-affecting metadata input is historically recoverable.
20. Release metadata provenance remains distinct from active
    metadata.
21. Channel transmission remains distinct from artifact consumption.
22. Authors never duplicate governed Book facts.
23. AI cannot choose authoritative metadata or identifier inputs.
24. Missing optional metadata is never fabricated.
25. The architecture remains additive-compatible with Edition, ONIX,
    Cover, and Distribution futures.

## 32. Explicit Non-Goals

No serializer code, migrations, schema, artifact changes, release
changes, ISBN assignment, Edition architecture, ONIX, retailer
metadata/APIs, distribution, cover production, barcodes, metadata
agency integration, pricing, royalties, analytics, manufacturing, or
AI metadata drafting. Blueprint only.

## 33. Phase 2 Implementation Boundary

**In:** finalized-version consumption with the pin; the Artifact
Metadata Provenance companion; the metadata fingerprint canon;
identifier-consumption provenance for the honestly consumable case
(externally evidenced assignments, human-selected); consumption
readiness; hgp-epub successor (package metadata of §13–§14);
hgp-print successor (title-page imprint line + copyright page of
§15–§16); the widened reproducibility key; deterministic
regeneration; Desk generation workflow and artifact provenance
display; RLS; tests; production verification; as-built record;
terminology ratification.

**Out (each its own future authorization):** every §32 exclusion;
release-side metadata recording (§22); channel transformation (§23);
EPUB visible-content additions; any consumption of
institution-acquired identifiers (none exist; Edition-gated, §12).
Not every ISBN case must be consumable — Phase 2 ships only what the
Edition boundary proves honest.

## 34. Future Edition / ONIX / Cover / Distribution Pressures

- **Edition** — will formalize format grouping and take over ISBN
  anchoring and assignment; consumption records are Edition-ready
  (additive reference, no rewrite).
- **New institutional ISBN assignment** — deferred with Edition;
  recorded-only identifiers await it (§12).
- **ONIX / metadata export** — will serialize pinned metadata
  versions + registrations + publisher identity deterministically;
  the fingerprint canon is its input discipline.
- **Cover Production** — will consume title/byline from pinned
  metadata, the consumed print ISBN for the barcode, and recorded
  page counts **(existing)**.
- **Barcode** — cover territory, untouched.
- **Distribution / retailer metadata** — will transmit pinned
  versions through the channel seam (§23), preserving what was sent.

## 35. Founder Office Determinations Required

**None.** The three likely questions resolve from repository
authority: (1) honest ISBN consumption is modelable without Edition
for externally evidenced assignments as per-artifact restatement
(§12), and every other case is deferred rather than weakened; (2)
publisher/imprint presentation follows the Phase 2 authorization's
standing rule — the imprint for reader-facing bibliographic
presentation, the legal entity where legal provenance warrants
**(existing)**; (3) historical-version selection authority follows
the existing artifact-generation authority with a recorded reason —
no new authority class is needed.

## 36. Final Architectural Determination

Metadata consumption enters the institution the way every capability
has: as an explicit, immutable, evidence-honest record of a human
act. The Candidate stays the manuscript's truth; the Bibliographic
Record stays the description's truth; the artifact — and only the
artifact — binds them, version-pinned and fingerprinted, so that
every future reader of the record can answer *exactly what did these
bytes say, and from which governed inputs* without trusting anything
but the record itself. Identifiers enter only where external evidence
already put them; nothing is assigned, inferred, or fabricated; and
Editions, ONIX, covers, and distribution find their seams cut and
waiting. Phase 2 can implement this without reopening any approved
architecture.
